# 未分類作品をすべて分類する方法

## 結論

未分類作品は、単発の一括更新スクリプトではなく、専用の「未分類整理センター」で段階的に処理する。

AIの回答をそのまま本番へ反映せず、次の流れを固定する。

1. 対象抽出
2. AI用JSONの書き出し
3. AI回答のステージング
4. 検証・差分確認
5. 承認
6. 100作品単位で反映
7. 完了後の再集計

途中で画面を閉じても、処理位置と承認結果をサーバー側に保存して再開できる設計とする。

## 1. 対象の定義

「未分類」は次の2段階に分ける。

- 完全未分類: ジャンルとテーマがどちらも0件
- 部分未分類: ジャンルまたはテーマのどちらかが0件

タグは個人用の管理印なので、未分類判定には使わない。

初期対象は完全未分類とする。完全未分類が完了した後、部分未分類を別バッチで処理する。

## 2. 最初に表示する棚卸し

整理センターを開いた時点で、現在のDBから次を集計する。

- 全作品数
- 完全未分類数
- ジャンルのみ設定済みの数
- テーマのみ設定済みの数
- ジャンル・テーマ設定済みの数
- 作品種別ごとの未分類数
- 状態ごとの未分類数

過去の書き出しファイルの件数は参考値に留め、実行時のDBを正とする。

## 3. AIへ渡す単位

1回のAI依頼は20作品を基本とし、最大50作品までとする。

1作品ずつ調査する方式より速く、100件以上を一度に渡す方式よりも回答崩れや取り違えを抑えやすい。

AI用JSONには次を含める。

- batch_id
- schema_version
- 標準分類語彙
- 分類の定義と上限
- 各作品のwork_id
- 各作品のversion
- title
- type
- creator
- release_year
- 現在のgenre、theme、tag

一言メモ、評価、お気に入り、進捗は分類判断に使わず、AIへ送らない。

## 4. AIへの指示

プロンプトでは次を固定する。

- ジャンルは作品の一般的な分野として1〜3件
- テーマは作品の主題として1〜5件
- 標準語彙を最優先する
- 新しいタグを作らない
- 作品を特定できない場合は空配列にする
- work_idとversionを変更しない
- 回答はjsonコードブロック1個だけ
- コードブロックの前後に説明を書かない

AI回答の各作品には、分類に加えて確認用の状態を持たせる。

```json
{
  "work_id": "...",
  "version": 1,
  "labels": {
    "genre": ["ビジネス・経済"],
    "theme": ["組織", "意思決定"]
  },
  "confidence": "high",
  "needs_review": false
}
```

`confidence`と`needs_review`は確認画面の並び替えにだけ使い、作品データには保存しない。

## 5. ステージング時の検証

貼り付けられた回答は、次をすべて満たすまで反映可能にしない。

- JSONコードブロックが1個だけ
- batch_idとschema_versionが一致
- work_idが対象バッチ内に存在
- versionが書き出し時と一致
- 同じwork_idが重複していない
- ジャンル3件以内
- テーマ5件以内
- 各分類40文字以内
- 空文字や重複がない
- 表記揺れが正規化できる
- 新規語彙が既存語彙と区別されている

対象から漏れた作品は「未回答」として残し、再依頼できるようにする。

## 6. 確認画面

確認画面では、作品ごとに次を横並びで表示する。

- 作品名・作者
- 現在の分類
- AI候補
- 標準語彙との一致状態
- 新規候補
- confidence
- 承認・修正・保留

初期状態は次のとおりとする。

- 標準語彙と一致する候補: 承認候補
- 表記揺れから標準語彙へ変換できる候補: 変換後を承認候補
- 標準語彙にない候補: OFF
- confidenceがlow、またはneeds_reviewがtrue: 保留

一括操作として、次を用意する。

- 高信頼かつ既存語彙だけをすべて承認
- 新規候補をすべてOFF
- 保留だけを表示
- 作品種別ごとに表示

## 7. 本番反映

反映は100作品単位で停止する。

- 1APIあたり20作品
- 1操作あたり最大5API
- 100作品ごとに自動停止
- 「次の100件を反映」で再開
- 反映済み位置をサーバーに保存
- 途中でブラウザーを閉じても再開可能

各作品はversionを照合し、書き出し後に編集された作品は競合としてスキップする。

既存分類は原則保持し、空欄の区分だけを補完する。既存分類の整理・移動を伴う場合は、未分類補完とは別の「分類語彙整理バッチ」で扱う。

## 8. 取り消しと監査

バッチごとに反映前の分類を保存する。

- 誰が承認したか
- いつ反映したか
- AI候補
- 最終的に反映した分類
- 反映前の分類
- 競合・スキップ理由

完了後も、バッチ単位で元の分類へ戻せるようにする。

## 9. 状態管理

バッチ状態は次を想定する。

- draft: 対象抽出前
- exported: AI用JSONを書き出し済み
- staging: AI回答を取り込み中
- review: 確認待ち
- approved: 反映可能
- applying: 本番反映中
- completed: 完了
- failed: 要確認
- rolled_back: 取り消し済み

## 10. 実装順

### PR A: 棚卸しと書き出し

- 未分類件数API
- 対象抽出
- 20作品単位のAI用JSON
- コードブロック限定プロンプト
- バッチ保存

### PR B: 回答の取込と確認

- JSON取込
- 検証
- 標準語彙との照合
- 新規候補の判定
- 作品ごとの承認・修正・保留

### PR C: 反映・再開・取り消し

- 100作品単位の反映
- version競合
- 途中再開
- 監査ログ
- バッチ単位の取り消し

## 11. 採用しない方法

### AI回答を直接DBへ一括投入

誤分類、作品の取り違え、表記揺れの大量発生を止められないため採用しない。

### 1,000作品前後を1つのプロンプトへ入れる

回答の欠落、順番のずれ、JSON破損が起きやすいため採用しない。

### ローカルの使い捨てスクリプトだけで更新

再開、差分確認、監査、取り消しが弱いため、本番運用の中心にはしない。

## 12. 完了条件

- 完全未分類が0件
- 保留作品が一覧化されている
- 新規語彙が無断登録されていない
- タグが変更されていない
- すべての反映に監査記録がある
- 完了後の書き出しでgenre、theme、tagが分離されている
- バッチの反映前状態へ戻せる
