## 実測: もっさりの原因

推測を避けるため、本番相当の規模(604件)をブラウザに投入して計測しました。

### 計測結果

| 計測項目 | 実測値 |
| --- | --- |
| **状態更新1回の合計(レイアウト確定まで)** | **805ms** |
| ├ 同期JavaScript | 190ms |
| └ レイアウト計算 | **610ms** |
| `renderWorkList()` 単体 | 123ms |
| ├ HTML文字列の生成 | 9ms |
| └ innerHTML のDOM構築 | 99ms |
| `filteredWorks()`(絞り込み＋並び替え) | 0.3ms |
| `shelfData()` / `themeData()`(棚の集計) | 0.3ms / 0.2ms |
| `renderHome()` | 4.7ms |
| 一覧のDOMノード数 | 13,981個(1カードあたり23個) |
| 一覧の総高さ | 199,183px |

### 原因

**データ処理は無罪です。** 絞り込みも並び替えも棚の集計も、合計1ms未満で終わっています。

重いのは描画です。604件すべてを毎回DOMに作り直し、そのすべてをブラウザにレイアウトさせています。
レイアウトだけで610msかかり、状態が変わるたびにこれが走ります。

**これが走る頻度が問題です。** 現状、次の操作すべてで全604件が再描画されます。

- 検索欄の1打鍵ごと(`setFilters()` が即座に通知するため、デバウンスが効いていません)
- カードの★を1つ押すたび
- メモを1件書き足すたび
- ホーム画面にいるときでも(表示していない一覧まで描画しています)

### 対策の効果を実測しました

`.work-card` に `content-visibility:auto` を当てると、画面外のカードのレイアウトをブラウザが省略します。

| 状態 | 状態更新1回 |
| --- | --- |
| 現状 | 797ms |
| `content-visibility:auto` 適用後 | **159ms** |

**CSS1行で5.0倍速くなります。** カードの高さはほぼ均一(320px)のため、
`contain-intrinsic-size: auto 320px` を添えればスクロールバーのがたつきも抑えられます。

## PR-1: 描画コストの削減

### 変更1: `content-visibility` を当てる(効果最大)

`public/styles/app.css` に1行追加します。

```css
.work-card{content-visibility:auto;contain-intrinsic-size:auto 320px}
```

`auto` キーワード付きの `contain-intrinsic-size` は実際の描画高さを記憶するため、
一度表示した範囲はスクロールしても高さが安定します。

### 変更2: 表示していないビューを描画しない

現状、`notify()` はすべての購読者を実行します。ホーム画面で★を押しても、
表示していない作品一覧の再描画(145ms)が丸ごと無駄に走ります。

`renderWorkList()` と `renderHome()` の先頭で、担当ビューが非表示なら描画を打ち切ります。

```js
export function renderWorkList() {
  if (state.view !== "library") { workListDirty = true; return; }
  // …既存の描画…
}
```

ビューを切り替えたときに描画し直す必要があるため、`applyView()`(`public/app.js:12`)から
再描画を促します。**ここを忘れると、ホームで★を押してから一覧へ移動したときに古い表示が残ります。**

### 変更3: 検索入力のデバウンス

`public/views/library.js:241` の入力ハンドラは、`setFilters()` を打鍵ごとに直接呼んでいます。
`clearTimeout`/`setTimeout` は `setView()` にしか掛かっておらず、再描画は抑止できていません。

```js
$("#globalSearch").addEventListener("input", (e) => {
  const value = e.target.value;
  clearTimeout(timer);
  timer = setTimeout(() => { setFilters({ q: value }); setView("library"); }, 80);
});
```

80msは、打鍵の連射中は描画せず、指を止めた瞬間には反応する体感の境目です。

### 変更4(判断が必要): 描画件数の上限

変更1〜3のあとも、`renderWorkList()` のDOM構築コスト145msは残ります。
これは描画する枚数に比例するため、削るには表示件数を絞るしかありません。

**まず変更1〜3だけを入れて実測することを勧めます。** 体感で足りるなら、上限は入れません。
全件常駐の利点(検索がゼロ待ち)は絞り込み側にあり、描画まで全件である必要はないため、
足りない場合は「先頭100件＋スクロールで追加」を後から足せます。

なお、再構築時に「続きを表示」ボタンは削除済みです(`public/views/library.js:304`)。
上限を入れる場合はここを別の形で戻すことになります。

### 確認方法

1. 作品を数百件持つ状態で、検索欄に連続入力しても引っかからないこと
2. カードの★を押したときの反応が即座であること
3. ホーム画面で★を押しても、一覧の再描画が走らないこと(開発者ツールで確認)
4. ホームで★を押した後に一覧へ移ると、評価が反映されていること(変更2の取りこぼし確認)
5. 一覧を最下部までスクロールしても、位置が飛んだり詰まったりしないこと

## PR-2: 抽選5作品カードに★とメモ入力を追加

### 実装方針

一覧カードと同じ部品をそのまま使います。`cardRatingMarkup()` は `public/core/format.js` に
共通化済みのため、`randomPickMarkup()`(`public/views/home.js:23`)へ差し込むだけです。

### 先に直す必要がある点

**抽選カードは `state.works` から引き直していません。**
`drawRandomPicks()` は `pickRandomWorks()` の戻り値をモジュール変数 `randomPicks` に保持します。
★を押すと `state.works` は更新されますが、`randomPicks` が抱えるオブジェクトは古いままです。
このままでは★を押しても抽選カードの表示が変わりません。

「現在読んでいる本」カードで同じ問題に当たったため、同じ対処をします。
描画時にIDだけを保持し、実データは `state.works` から引き直します。

```js
function renderRandomPicks() {
  const picks = randomPickIds.map((id) => state.works.get(String(id))).filter(Boolean);
  // …描画…
}
```

### メモ入力の開閉状態

一覧カードの開閉状態は `public/views/library.js` のモジュール変数 `openNoteCardIds` が持っています。
ホーム側でも使うため、この集合と保存処理を `public/core/` へ移して共有します。
保存処理(`POST /api/works/:id/notes`)も同じものを使い回せます。

### 確認方法

1. 抽選カードから、詳細を開かずに★を付けられること
2. ★を押しても5冊の顔ぶれが変わらないこと
3. 抽選カードからメモを書き足せること。保存後も入力欄が開いたままであること
4. 同じ作品が一覧にも出ている場合、両方の★表示が揃うこと

## PR-3: 読み込み中のスケルトン表示

### 現状

`public/styles/app.css` に `@keyframes` は**1つもありません**。動きは `transition` のみです。
読み込み中の表示も、文字で「読み込み中…」と出しているだけです。

起動時は `/api/me` の応答後に `/api/home` と `/api/library/snapshot` を待つため、
その間ホーム画面はほぼ空のまま止まって見えます。

### 変更内容

作品カード・抽選カード・棚の形に合わせたスケルトンを出します。
背景をゆっくり左右に流す `shimmer` を1つ定義し、共通クラスとして使い回します。

```css
@keyframes skeleton-shimmer{from{background-position:-200% 0}to{background-position:200% 0}}
.skeleton{background:linear-gradient(90deg,var(--surface-2) 25%,var(--surface) 50%,var(--surface-2) 75%);background-size:200% 100%;animation:skeleton-shimmer 1.4s ease-in-out infinite;border-radius:8px}
```

適用先は次の3か所です。

| 場所 | 現状 | 変更後 |
| --- | --- | --- |
| ホームの抽選枠 | 「読み込み中…」の文字 | カード5枚分のスケルトン |
| 作品一覧 | 「読み込み中」の文字 | カード数枚分のスケルトン |
| ジャンル棚・テーマ棚 | 空 | 棚の形のスケルトン |

### 忘れてはいけない対応

`public/styles/app.css:431` の `prefers-reduced-motion` は `transition` しか止めていません。
`animation` を追加するため、この行も合わせて拡張します。

```css
@media(prefers-reduced-motion:reduce){*{scroll-behavior:auto!important;transition:none!important;animation:none!important}}
```

既存テストがこの指定の存在を検証しているため(`test/genre-shelf-v15.test.js`)、
指定を消さずに拡張してください。

### 確認方法

1. 通信を低速にした状態で読み込み、スケルトンが出てから実データに置き換わること
2. OSの「視差効果を減らす」設定を有効にすると、点滅せず静止した状態で表示されること
3. データが0件のときに、スケルトンのまま止まらず空表示に切り替わること

## 実装順序

1. **PR-1**。体感への効果が最も大きく、他と独立しています
2. **PR-3**。PR-1で描画が速くなるとスケルトンの出番は減りますが、初回読み込みでは依然として有効です
3. **PR-2**。PR-1の「表示していないビューを描画しない」と関わるため、最後に回すのが安全です
